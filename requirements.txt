# What belongs where:
#   requirements.txt         the framework (`odoo/`) plus the always-loaded
#                            addons — what every server process imports no
#                            matter which modules are installed
#   requirements-addons.txt  dependencies reached from one bundled addon, owned
#                            by the module that imports them
#   requirements-test.txt    needed to RUN the suites, not to run the server
#   requirements-dev.txt     linters, type checkers, native-extension build tools
#
#   cbor2 (6.x)         major; auth_passkey's vendored webauthn decodes with it.
#                       Nothing outstanding: 5.9.0 fixes GHSA-3c37-wwvx-h642
#                       (HIGH, uncontrolled recursion in cbor2.loads), which
#                       _vendor/webauthn/helpers/parse_cbor.py reaches with
#                       attacker-supplied bytes from an unauthenticated
#                       endpoint. 5.8.0 was not a tenable floor for that path.
#   cryptography (50.x) four majors across 54 call sites. 46.0.7 ends the 46.x
#                       line and clears three of the seven advisories open
#                       against 46.0.4: GHSA-r6ph-v2qm-q3c2 (HIGH, missing
#                       subgroup validation on SECT curves), GHSA-p423-j2cm-9vmq
#                       (MODERATE, buffer overflow on non-contiguous buffers)
#                       and GHSA-m959-cc7f-wv43 (LOW, DNS name constraints).
#                       Four need a major and are the standing cost of the hold:
#                       GHSA-537c-gmf6-5ccf (HIGH, vulnerable OpenSSL in the
#                       wheels) at 48.0.1; GHSA-jwv3-5hgf-82ww (HIGH,
#                       exponential path-building) and GHSA-m2h6-j472-rp4c
#                       (MODERATE, wildcard escape from permittedSubtrees) at
#                       49.0.0; GHSA-g6cj-pr64-35w5 (HIGH, Bleichenbacher oracle
#                       in PKCS#7 EnvelopedData decryption) at 50.0.0. None of
#                       those four is reachable on its own: pyopenssl 25.3.0
#                       caps this at <47, so the first of them costs a pyopenssl
#                       bump too. See the ladder above.
#   pyopenssl (26.x)    major, and the one hold with no patch available inside
#                       it: GHSA-5pwr-322w-8jr4 (HIGH, DTLS cookie callback
#                       buffer overflow) and GHSA-vp96-hxj8-p424 (LOW, TLS
#                       bypass via an unhandled servername-callback exception)
#                       are both fixed only in 26.0.0, so 25.3.0 carries them
#                       until the major lands. Per the ladder above, 26.0.0
#                       accepts the cryptography 46.0.7 already pinned here, so
#                       this is the one rung that needs no companion bump — and
#                       every pyopenssl API this fork uses was probed against
#                       26.0.0 and is unchanged (OpenSSL.crypto.Error,
#                       OpenSSL.SSL.Error, VERIFY_PEER,
#                       VERIFY_FAIL_IF_NO_PEER_CERT, X509, X509Store,
#                       X509StoreContext, X509StoreContextError,
#                       urllib3.contrib.pyopenssl's PyOpenSSLContext /
#                       get_subj_alt_name / inject_into_urllib3, and
#                       use_certificate() / use_privatekey() on in-memory
#                       material). The only call site that breaks on 26.0.0 —
#                       l10n_it_edi/tools/remove_signature.py, which reaches
#                       into OpenSSL._util.lib for PKCS7_verify — is ALREADY
#                       broken on 25.3.0: cryptography no longer compiles the
#                       PKCS7_* CFFI bindings and pyopenssl no longer exports
#                       load_pkcs7_data, so that strategy raises AttributeError
#                       either way and its suppress(Exception) hides it. It is
#                       not a blocker for this bump; it is its own defect.
#                       pyopenssl is load-bearing, not legacy cruft: mail
#                       servers store certificate material in the database and
#                       base/ir_mail_server.py feeds it to a PyOpenSSLContext
#                       via _ctx.use_certificate()/use_privatekey(), which
#                       stdlib ssl cannot do — load_cert_chain() takes file
#                       paths only, so dropping it would mean writing private
#                       keys to disk. Also reached by auth_passkey's vendored
#                       webauthn (chain validation), certificate/, l10n_it_edi
#                       (PKCS#7 via private OpenSSL APIs) and enterprise
#                       l10n_nl_reports. Removing it is a project, not a bump.
#   reportlab (5.x)     major; PDF output needs visual comparison. No advisory
#                       open against 4.4.10 — this hold costs nothing today.
