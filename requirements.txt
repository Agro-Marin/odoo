# What belongs where:
#   requirements.txt         the framework (`odoo/`) plus the always-loaded
#                            addons — what every server process imports no
#                            matter which modules are installed
#   requirements-addons.txt  dependencies reached from one bundled addon, owned
#                            by the module that imports them
#   requirements-test.txt    needed to RUN the suites, not to run the server
#   requirements-dev.txt     linters, type checkers, native-extension build tools
#
#   cbor2 (6.x)         major; auth_passkey's vendored webauthn decodes with it.
#                       Nothing outstanding: 5.9.0 fixes GHSA-3c37-wwvx-h642
#                       (HIGH, uncontrolled recursion in cbor2.loads), which
#                       _vendor/webauthn/helpers/parse_cbor.py reaches with
#                       attacker-supplied bytes from an unauthenticated
#                       endpoint. 5.8.0 was not a tenable floor for that path.
#   reportlab (5.x)     major; PDF output needs visual comparison. No advisory
#                       open against 4.4.10 — this hold costs nothing today.
#
# Not held — at the current release, and pinned together because they move
# together. cryptography and pyopenssl are a single upgrade unit: each pyopenssl
# release narrows the cryptography version it accepts (25.3.0 took <47, 26.2.0
# <49, 26.4.0 <51), so bumping either alone stalls at the other's cap.
#
#   cryptography        50.0.0, with nothing outstanding. It clears the last
#                       four advisories the 46.x line carried:
#                       GHSA-537c-gmf6-5ccf (HIGH, vulnerable OpenSSL in the
#                       wheels) at 48.0.1; GHSA-jwv3-5hgf-82ww (HIGH,
#                       exponential path-building) and GHSA-m2h6-j472-rp4c
#                       (MODERATE, wildcard escape from permittedSubtrees) at
#                       49.0.0; GHSA-g6cj-pr64-35w5 (HIGH, Bleichenbacher oracle
#                       in PKCS#7 EnvelopedData decryption) at 50.0.0. All 54
#                       call sites across odoo, enterprise and agromarin were
#                       probed on 50.0.0 against 46.0.7 side by side with
#                       DeprecationWarning raised as an error; the two behave
#                       identically, including the three most exposed to a
#                       major — hazmat.decrepit's TripleDES (payment_redsys),
#                       hazmat.backends.default_backend() (agromarin
#                       documents_l10n_mx_edi) and pkcs7.PKCS7SignatureBuilder
#                       (enterprise l10n_ar_edi), all three still present.
#                       Two notes for whoever takes 51.x: the PKCS#7 advisory
#                       covers EnvelopedData DECRYPTION, which nothing here
#                       performs (l10n_ar_edi only signs); and
#                       iot_drivers/tools/certificate.py still reads the
#                       not_valid_after PROPERTY, deprecated since 42 in favour
#                       of not_valid_after_utc and still merely deprecated on
#                       50.0.0 — latent debt, not a break, but it is the one
#                       call site a removal would take out.
#   pyopenssl           26.4.0, the companion 50.0.0 requires (26.3.0+ needs
#                       cryptography>=49). Nothing outstanding: the two
#                       advisories that made 25.3.0 untenable —
#                       GHSA-5pwr-322w-8jr4 (HIGH, DTLS cookie callback buffer
#                       overflow) and GHSA-vp96-hxj8-p424 (LOW, TLS bypass via
#                       an unhandled servername-callback exception) — are fixed
#                       in 26.0.0, and no advisory affects 26.x at all. Probed
#                       the same way, 26.4.0 against 25.3.0: OpenSSL.crypto.Error,
#                       OpenSSL.SSL.Error, VERIFY_PEER / VERIFY_NONE /
#                       VERIFY_FAIL_IF_NO_PEER_CERT, X509.from_cryptography,
#                       X509Store, X509StoreContext(Error),
#                       crypto.load_certificate / load_privatekey / FILETYPE_PEM
#                       (enterprise l10n_nl_reports), urllib3.contrib.pyopenssl's
#                       PyOpenSSLContext / get_subj_alt_name /
#                       inject_into_urllib3, and _ctx.set_verify() /
#                       use_certificate() / add_extra_chain_cert() /
#                       use_privatekey() / check_privatekey() /
#                       get_cert_store().add_cert() on in-memory material.
#                       One call site fails on every version in range and so is
#                       nobody's regression:
#                       l10n_it_edi/tools/remove_signature.py reaches into
#                       OpenSSL._util.lib for PKCS7_verify, which cryptography
#                       no longer compiles into the CFFI bindings and pyopenssl
#                       no longer exports as load_pkcs7_data — that strategy has
#                       raised AttributeError since before 25.3.0 and its
#                       suppress(Exception) hides it. It is its own defect.
#                       pyopenssl is load-bearing, not legacy cruft: mail
#                       servers store certificate material in the database and
#                       base/ir_mail_server.py feeds it to a PyOpenSSLContext
#                       via _ctx.use_certificate()/use_privatekey(), which
#                       stdlib ssl cannot do — load_cert_chain() takes file
#                       paths only, so dropping it would mean writing private
#                       keys to disk. Also reached by auth_passkey's vendored
#                       webauthn (chain validation), certificate/, l10n_it_edi
#                       (PKCS#7 via private OpenSSL APIs) and enterprise
#                       l10n_nl_reports. Removing it is a project, not a bump.
