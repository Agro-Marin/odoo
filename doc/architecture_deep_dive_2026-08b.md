This is the **second** architecture pass. The first
(`architecture_audit_2026-08.md`, plus `architecture_inventory_2026-08.md`)

## Legend

- 🔴 **Defect** — provable wrong behaviour.
- 🟠 **Structural risk** — works today, one edit away from breaking; no gate.
- 🟡 **Asymmetry / smell** — inconsistency that costs comprehension.
- 🟢 **Verified good** — explicitly checked, no action. Recorded so a later pass
  does not re-explore it.

## How this pass was conducted

Two complementary methods, because reading 126 kLOC linearly finds nothing that
a mature codebase has not already fixed:

1. **Whole-tree mechanical analysis** — every one of the 536 files, every time:
   an AST inventory (LOC, module docstring, nesting depth, longest function,
   bare/`pass` handlers, mutable defaults), a longest-function ranking, the
   `nodoc` distribution per package, and an assertion-quality scan over every
   test suite.
2. **Targeted deep reads** — full reads of the seams and of the newest,
   least-battle-tested code, where defects are likeliest: the ORM's pure-Python
   engine (`components/`), the Layer-1 inversion seam, `Transaction`, and the
   fork-specific HTTP features (`_params.py`, `openapi.py`, `routing.py`).

### G1 🟠 The subsystem map was ungated, and had drifted into depicting four directories that do not exist

The first audit's **F3** found `odoo/ARCHITECTURE.md`'s subsystem map had
drifted, and its **P3** proposed two things: repair the drift, *and* build a gate
so it cannot recur. **Only the first was done.** Verified:

```
$ grep -rn "ARCHITECTURE.md" tooling/ --include=*.py
tooling/architecture/layer_check.py:5     (a docstring reference)
tooling/architecture/layer_check.py:94    (a comment)
tooling/architecture/mixin_coupling_check.py:5  (a docstring reference)
```

No tool read the file. `doc_link_gate.py` proves a referenced `.md` *exists*;
nothing proved a described package still matched its directory. So the
descriptive half of the architecture docs was exactly as ungated as F3 said, and
it had drifted again.

The map is drawn as an ASCII **directory tree**:

```
├── db/             Decomposed sql_db.py + the resilience tier (flat modules)
│   ├── connectivity   pool, cursor, ddl, savepoint, schema_cache, bulk, …
│   └── resilience     breaker (…), lag (…), budget (…), …
├── http/           Decomposed http.py (flat modules)
│   ├── serving     application, dispatcher, routing, session, request_class, …
│   └── features    openapi (…), _params (…), geoip, helpers, constants, …
```

`db/connectivity`, `db/resilience`, `http/serving` and `http/features` **do not
exist**. Both packages are flat. They are *logical groupings* rendered in a
notation that means "subdirectory", so a reader following the map looks for
`odoo/http/serving/routing.py`. The parenthetical "(flat modules)" added by the
concurrent edit is a prose disclaimer contradicting the notation beside it, not
a fix.

### G2 🟢 No test in the core suites asserts a literal against a literal

The first audit found one genuinely vacuous test by hand
(`db/tests/test_lag.py`). I scanned for the whole class mechanically — every
`assertX(...)` or bare `assert` whose every argument is a compile-time literal,
across `odoo/orm`, `odoo/db`, `odoo/http`, `odoo/libs`, `odoo/tools`,
`odoo/tests`, `tests/` and `tooling/`: **0 hits**.

`mock.assert_called_once_with("literal")` is deliberately excluded — its literals
are the assertion's substance, not a tautology. An earlier, looser version of the
scan flagged 72 tests almost entirely on that pattern; the number is recorded
only to say that it was noise, not a finding.

### G3 🟢 The pure-Python ORM engine holds its documented invariants

`components/` is the part of the ORM most exposed to silent breakage — it is
dependency-injected, so no import gate constrains its collaborators. Read in
full (`core.py`, `cache.py`, `compute.py`, `unit_of_work.py`), checking each
docstring claim against the code:

- **"dirty ⇒ value present"** — upheld on every path. `FieldCache.invalidate`'s
  `keep_dirty` branch, `invalidate_all`, and `OrmCore.find_pending_write` are
  mutually consistent, and `find_pending_write` materialises a one-shot `ids`
  iterator before scanning (a generator consumed by the first dirty field would
  make the guard silently pass for every later one).
- **`_pending`/`_dirty` hold only non-empty sets** — both `schedule()` and
  `mark_dirty()` return early on empty input *without* touching the
  `defaultdict`, which is what makes `field in _pending` a valid O(1) answer on
  the `Field.__get__` hot path.
- **Stall detection is snapshot-based, not count-based** — and the docstring
  explains why a count cannot work (a cycle can trade one entry for another).
  `SNAPSHOT_AFTER` is justified with a measurement (3.6% on a 1000-record
  `create`).

No action. Recorded because "no import edge" is exactly why this package would
otherwise go unexamined.

### G4 🟢 The typed-route contract survives the traps its own docstring names

`http/_params.py` promises a clean 400 for anything that is not the declared
type. The interesting cases all hold:

- `bool` is rejected before `int`/`float`/`str` in `_coerce_scalar`, so
  `True` does not silently become `1` or `"True"` (a real hazard, since
  `isinstance(True, int)`).
- `_reject_non_json_number` refuses Python-only number spellings (`"1_000"`,
  non-ASCII digits) that `int()`/`float()` would otherwise accept — the
  request contract does not inherit Python's literal grammar.
- Non-finite floats (`inf`, `nan`) are rejected, so a JSON body cannot smuggle a
  value that has no JSON representation.
- `build_param_specs`' `params[1:]` (dropping `self`) is **correct**: every
  caller passes the *undecorated* function — `routing.py:519` via
  `_original_endpoint`, and `openapi.py` via `endpoint.original_endpoint` — never
  a bound method.

One thing worth noting rather than fixing: `ParamSpec.allow_none`'s docstring
claims to cover both `X | None` and `Optional[X]`, but `_resolve` tests only
`isinstance(annotation, types.UnionType)`. That is correct **only because the
runtime is pinned to Python 3.14**, where `typing.Union` *is* `types.UnionType`
(verified: `isinstance(typing.Optional[int], types.UnionType)` → `True`). On any
earlier interpreter the `Optional[X]` half of the claim would be false and those
parameters would silently pass through uncoerced. The runtime floor is pinned in
`odoo/release.py` (MIN = MAX = 3.14), so this is sound today; it is the kind of
correctness that rests on a pin rather than on the code.

### G9 🟢 The restore scanner survives 2000 seeds nobody had run, against real psql

`odoo/service/_dump_scanner.py` is the framework's sharpest security boundary:
it decides whether an **attacker-supplied** database dump may be fed to
`psql -f`, where a single un-caught `\!` is remote code execution as the Odoo
service account. It is also fork-specific and recent, so it is exactly where
this pass should look rather than re-reading the ORM.

It is already defended unusually well — 42 unit tests, a fixed corpus of seven
hand-found bypasses, and a *generative differential* fuzzer that builds
dump-shaped SQL from a grammar of psql's lexical contexts and checks the
one-way property `the canary fired ⇒ the scanner rejected` against real `psql`.
The suite commits 150 seeds; the author's notes record 3000 run by hand.

**What this pass added: seeds 3000–4999 — 2000 cases never previously
exercised — against real PostgreSQL 18.4.**

| | result |
|---|---:|
| cases | 2000 |
| `psql` really executed the shell payload | **350 (17.5%)** |
| scanner flagged | 1087 (54.4%) |
| **bypasses** | **0** |

The middle row is the one that matters, and it is why I ran a counting driver
rather than the plain entry point: `0 bypasses` is satisfied vacuously by an
empty antecedent, so a run in which `psql` never executed the payload would
prove nothing while looking identical to a clean result. 350 genuine executions
with zero bypasses is evidence; "0 bypasses" alone would not have been. The rate
also corroborates the author's independently measured 16% over their 3000.

Also verified in passing: `_assert_dump_sql_safe` is genuinely *on* the restore
path (`db.py:1089`, before `psql` is invoked at 1091) rather than merely
existing — a control that is never called is worth nothing — and the surrounding
zip handling has both zip-slip (`Path.resolve()` + `is_relative_to`) and
zip-bomb (`_unpack_budget`, an expansion-ratio cap) protection, plus a
wall-clock timeout on the restore subprocess.

No action. Recorded so the next pass knows this boundary has been probed 5000
seeds deep and can spend its budget elsewhere.

### G8 🟡 The dump scanner's fuzzer documented an invocation that cannot run

`tests/contract/test_psql_scanner_fuzz.py` is the generative differential that
compares the restore scanner against real `psql`. Its docstring offers an escape
hatch for widening the search during an investigation:

```
    python tests/contract/test_psql_scanner_fuzz.py <scratch-db> 3000
```

**That command has never worked.** The module imports
`odoo.service._dump_scanner` (needs the repo root on `sys.path`) *and*
`from .conftest import requires_pg, requires_psql` (a relative import, needs the
module loaded as part of a package). Running the file by path satisfies neither,
so it dies at line 38 or 40 — before the `if __name__ == "__main__":` block it
documents is ever reached. Measured, both failure modes:

```
$ python tests/contract/test_psql_scanner_fuzz.py db 2
ModuleNotFoundError: No module named 'odoo'
$ PYTHONPATH=. python tests/contract/test_psql_scanner_fuzz.py db 2
ImportError: attempted relative import with no known parent package
$ PYTHONPATH=. python -m tests.contract.test_psql_scanner_fuzz db 2
2 cases, 0 bypasses          <- the form that works
```

The `__main__` block is carefully written and carries
`# pragma: no cover - investigation entry point` — the marker that also explains
why nobody noticed: it is excluded from coverage *and* unreachable, so no signal
existed in either direction. This is the one place in a rigorously verified
module where the verification tool's own escape hatch was itself unverified.

**Fixed** — the docstring now documents `python -m tests.contract.…` and states
why `-m` is required, so the next person widening the search does not lose time
to it.

Scoped, not overclaimed: four other modules share the shape (a `__main__` block
plus a top-level relative import), but none *documents* a script invocation and
CI runs them all under `pytest` — `freethreading.yml` invokes
`python -m pytest odoo/orm/components/tests/test_model_graph_freethreading.py`,
and `odoo/tests/test_module_operations.py` already documents the correct
`python -m odoo.tests.test_module_operations`. Only this one was wrong.

## What was delivered

### `tooling/architecture/subsystem_map_check.py` — the gate P3 proposed and never built

Sixth blocking checker in the `Architecture Boundaries` workflow, in the same
drift-zero posture as its siblings. It parses the subsystem map and enforces two
rules:

1. **No fictional paths.** Every path-shaped name in the map must exist. A
   logical grouping that is not a directory must write itself `[in brackets]`;
   the checker then treats it as a label and attributes the names after it to
   the enclosing package.
2. **An enumeration that starts must finish** — *per kind*. The map need not
   list a package's contents (`libs/` is 138 files summarised in one line), but
   a package whose children it *does* enumerate must be enumerated exhaustively:
   name one module and every module must be named; name one subpackage and every
   subpackage must be named.

Splitting rule 2 by kind is what keeps it proportionate. `tools/` lists
subpackages only, so the gate demands its three subpackages and not its 35
modules; `db/` lists modules only, so it demands all 17 and is silent about
subpackages. A blanket "list everything" rule would force 138 lines of `libs/`
into a map whose entire value is that it fits on a screen.

**The notation change is the load-bearing part.** The map now distinguishes what
is a path from what is a grouping, so the document states which of its nodes are
real — a distinction it previously left to the reader.

Repairs made to `odoo/ARCHITECTURE.md` so the gate starts at zero, like its
siblings:

- `connectivity` / `resilience` / `serving` / `features` → `[bracketed]`.
- `tools/` gained `pdf/` and `babel_extractors/`.
- The top level gained `upgrade_code/` and `addons/`.
- A **Notation** note stating the grammar the gate enforces.

### `tooling/architecture/test_subsystem_map_check.py` — 27 tests

### `tooling/architecture/package_index_check.py` — the same rule one level down (P3)

Seventh blocking checker. `subsystem_map_check.py` gates the top-level map;
this gates the two packages that document themselves **per module** —
`odoo/db/README.md`'s *Module map* (18 rows) and `odoo/_monkeypatches/README.md`'s *Patch
Index* (15 rows). Both were complete when measured, and both were unprotected.
`odoo/db/README.md` even instructs the reader to extend it ("Add the check here when
you add an invariant above") with nothing enforcing the instruction.

The rule is symmetric: every module in the package is in the index, and every
module in the index exists (`__init__.py` may be listed — `db/` does — but is
never required).

**The section scoping is the load-bearing part, and it is measured, not
asserted.** Both READMEs carry other tables that name `.py` files, and some of
those files are deliberately gone. Scanning the whole of
`odoo/_monkeypatches/README.md` instead of its *Patch Index* section names 21 modules
instead of 15, of which **six are phantoms** — `lxml`, `pytz`, `urllib3`,
`xlrd`, `xlwt`, `zeep`, every one correctly absent, listed in the *Recently
Removed* table. An unscoped gate would fail six times against a document that is
exactly right. Pinned by `test_section_scoping_is_load_bearing`, which asserts
the exact six.

17 tests. Proven by mutation against the real tree:

| mutation | gate |
|---|---|
| add `odoo/db/_probe_tmp.py` | **fails** (`exit 1`), names the file |
| add `odoo/_monkeypatches/_probe_tmp.py` | **fails**, names the file |
| index names a module that does not exist | **fails** (test) |
| probes removed | **exits 0** again |

Both READMEs now carry a short "**This table is enforced**" note at the index, so
the instruction and its gate sit together — the absence of which is what let
`odoo/ARCHITECTURE.md` drift in the first place.

#### Retraction: my analysis of this proposal was wrong

Earlier in this pass I wrote that the first audit's proposed fix — extract query

The original entry, as written before the refactor landed:

`scc_without_base` is 2 and the only residual cycle is `read ↔ search`
(`read → search` via `_search`, `_as_query`, `_field_to_sql`, `exists`;
`search → read` via `_fetch_query`, `_determine_fields_to_fetch`, `fields_get`).
Now that P1-metadata has landed and `max_scc` is 2, this is the *entire*
remaining coupling debt in the mixin decomposition, and the ratchet makes each
step measurable.

Resolving each back-edge member to the method that calls it:

```
$ mixin_coupling_check.py --explain search read
search -> read via 3 member(s): _determine_fields_to_fetch, _fetch_query, fields_get
```

All four call sites of those three members are inside **two methods**:

| method | line | calls into `read` |
|---|---:|---|
| `SearchMixin.search_fetch` | search.py:110 | `_determine_fields_to_fetch` ×2, `_fetch_query` |
| `SearchMixin.search_read` | search.py:708 | `fields_get` |

Nothing else in `search.py` reaches into `read.py` at all. Both are **composite
entry points** — "search, then fetch" and "search, then format" — that happen to
be hosted on `SearchMixin`. They are not search operations that need read; they
are compositions of the two.

So the move is the `_empty.py` (P5a) pattern inverted: rather than pushing a
shared leaf *down*, host the two composites *above* both mixins, in a new
`mixins/_search_read.py`. `search → read` then disappears entirely, `read →
search` remains as a one-way edge, and the graph becomes a **DAG**: `max_scc`
2 → 1, `cyclic_edges` 2 → 0.

Checked in advance:

- **MRO safety.** `search_fetch`/`search_read` would be defined in exactly one
  class, so resolution is unchanged and addon `super()` chains still reach them.
  No code anywhere in `odoo`/`enterprise`/`agromarin` names `SearchMixin` or
  `ReadMixin` directly (only a same-named *addon* class, `DateRangeSearchMixin`),
  so the ~13 addon overrides of `search_read`/`search_fetch` are all ordinary
  model-level overrides and are unaffected.

**Why it was not attempted here:** another session was editing
`odoo/orm/models/mixins/` throughout this pass — and, as it turned out, was
implementing this very refactor. Deferring was the right call for the wrong
reason: I expected a merge conflict, not a race to the same result.
