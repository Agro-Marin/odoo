# ADR-0071: One edge, one column — and the sequence is told directly

- **Status:** Accepted
- **Date:** 2026-08-26

## Context

A payment and its journal entry held each other. `account_payment.move_id` and
`account_move.origin_payment_id` were two columns for one relationship, and
nothing constrained them to agree. Both were live: the journal dashboard joined
the move's column, the payment's whole state machine read the payment's, and
`hr_expense` wrote both by hand — with a comment apologising for the recompute
chain the second write set off.

**The duplication was not laziness. It was an ordering constraint.**

`account.move._compute_name` assigns a move's sequence number, and
`_get_last_sequence_domain` decides which sequence applies by asking whether the
move is a payment's entry — in an ORM domain, and again in raw SQL:

```
AND origin_payment_id IS NOT NULL
```

A journal with `payment_sequence` set numbers payment entries in their own
series. So the answer has to be available **on the move, at create time** — and
`account.payment.move_id` cannot be written until the move exists. Passing
`origin_payment_id` in the move's create values was the only way to have it
early enough.

Reading it back later is not the same question. `origin_payment_id` was read
from roughly fifty places, fifteen of them localisations, plus a `related=` on
`account.move.line` and seven raw-SQL sites. A plan that counted the two
production *writes* and concluded the column could simply be dropped had counted
the wrong thing.

## Decision

**The edge is stored once, on `account.payment.move_id`.**

`account_move.origin_payment_id` keeps its name and its meaning as the head of
`account_move.payment_ids`, computed and searchable, with no column of its own.
Every Python reader, every `@api.depends`, every domain and every view is
unchanged; what changes is where the value comes from.

**The sequence is told directly rather than inferred from a column.**
`_get_last_sequence_domain` has always accepted `is_payment` in the context and
nothing ever set it — the move carried a column instead. `_generate_journal_entry`
now creates the move `with_context(is_payment=True)`, which is the honest
statement: *this entry is a payment's*, made by the code that knows it, at the
moment it is true. The clause that filters other moves in the journal asks the
payment table instead:

```
AND EXISTS (SELECT 1 FROM account_payment p WHERE p.move_id = account_move.id)
```

**A name a caller must know is a seam, and this one is now used.** `is_payment`
was a hook with no callers, which is indistinguishable from dead code; it is part
of the contract of creating a payment's entry from here on.

## Alternatives considered

**Leave both columns and make the second ORM-maintained** — `origin_payment_id`
as `compute=…, store=True, readonly=False`, so the create value is still honoured
and only `hr_expense`'s hand-written second write disappears. Cheaper and safer:
no migration, no SQL rewrites. Rejected because it keeps two columns for one
edge and leaves the sequence still inferring from a copy; it removes the accident
without removing the duplication. It was the recommended option when this was put
to the fork's owner, and the fuller collapse was chosen.

**Invert the creation order** — create the payment before its entry, so
`move_id` is available at create. Rejected: it is a redesign of payment posting
for the sake of a column, and the context key already carries the one fact the
move needs.

**Drop the name too, and make every reader spell `payment_ids[:1]`.** Rejected on
signal-to-noise: "the payment this entry was generated by" is what fifty readers
mean, and `payment_ids` is the ORM's spelling of an inverse rather than the
concept. The One2many exists because the ORM needs it to invalidate the compute,
not because multiplicity is real — a partial unique index on
`account_payment.move_id` would state that, and is not added here only because
the fork has not measured whether any deployment has ever produced two.

## Consequences

`account_move.origin_payment_id` is no longer a stored column: code that read it
in raw SQL had to be rewritten, and code that reads it through the ORM did not.
Seven SQL sites were rewritten to join `account_payment.move_id`.

Creating a payment's journal entry outside `_generate_journal_entry` without
`is_payment` in the context will number the entry in the journal's ordinary
series. That is the same behaviour `hr_expense` already had — it created its
moves before linking the payments, so `origin_payment_id` was empty when the name
was computed — but it is now a rule to know rather than an accident to discover.

The migration carries values from whichever column held them and refuses the
upgrade, naming the rows, where the two disagree.

## Enforcement

None, and the shape one would take is worth stating. The rule this record
protects — *do not reintroduce a second column for this edge* — is not
mechanically checkable without a general "two Many2ones over the same pair of
models" detector, which would fire on legitimate pairs (`account.move` carries
`statement_line_id` beside `payment_ids` for a different source document).

`account.bank.statement.line` still holds the shape this record rejects:
`move_id` on the line, `statement_line_id` on the move, both stored. It is left
alone deliberately — the statement line `_inherits` its move, so its `move_id` is
`required` and `ondelete="cascade"`, and the delegation makes the second column a
different argument from this one. A later record may take it; this one does not
pretend to.

## Amendments

### 2026-08-27 — the context is not the mechanism, and the rule stated below it is false

An audit of this record's own claims, run the day after it was accepted, measured
two of them wrong.

**`is_payment` is inert on every path this fork exercises.** *Decision* presents
it as what makes the sequence work. It does not: `_compute_name` runs when the
move is posted, on a recordset that no longer carries the context
`_generate_journal_entry` set, and by then `payment_ids` is populated — so the
computed `origin_payment_id` answers the question. Measured by removing the
`with_context(is_payment=True)` entirely: an ordinary payment still takes the
payment series, `PBNK1/…`, unchanged. The call stays because it is correct and
costs nothing for any future path that computes a name at create time, but it is
belt and braces, not the mechanism. **What actually carries the split is the
computed field**, which is the same thing the column carried before.

**The rule in *Consequences* is false in both halves.** Creating a payment's
entry outside `_generate_journal_entry` and linking the payment afterwards does
**not** number it in the ordinary series — it takes the payment series, because
the link populates `origin_payment_id` before the name is computed. And
`hr_expense` never relied on an empty column: it wrote
`move.origin_payment_id` explicitly right after creating its payments, so the
column was set before posting. Measured on both codebases with `hr_expense`'s
exact shape: `PBNK1/…` before this change and `PBNK1/…` after. **The behaviour is
unchanged; only this record's account of it was wrong.**

Two capability losses belong here and were not stated. A computed field is
neither orderable nor writable: `ORDER BY origin_payment_id` now raises
`Cannot convert account.move.origin_payment_id to SQL`, and a write to it raises
rather than storing. Nothing in this workspace does either — the field appears in
views only as `invisible="1"` — but an integration, a server action or a Studio
view outside it could. The same applies to `payment.transaction.payment_id`,
collapsed the same way in `14704e43e43`.
