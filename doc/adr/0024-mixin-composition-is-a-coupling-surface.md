# ADR-0024: Mixin composition is a coupling surface, and it has no import edges

- **Status:** Accepted
- **Date:** 2026-08-14 (retroactive — records decisions already enforced)

## Context

Every structural gate this fork has built reasons about **edges** — an import in
Python (ADR-0001, ADR-0005), an import or registry lookup in the client
(ADR-0019), a module specifier or an inherited member (ADR-0020, ADR-0021). That
model is right for every boundary in `doc/architecture/module.md` except one.

**A mixin composition produces no edge at all.** `BaseModel` is composed from a
couple of dozen empty-`__slots__` mixins by multiple inheritance; they
collaborate through `self`, and a `self._fields` or `self._search` call inside
one mixin resolves to a sibling at runtime while producing nothing an import
checker sees. The most intricate coupling surface in the framework was invisible
to the checker guarding everything around it.

The client has the same shape by a different mechanism: its search model is
composed from five mixin factories in a nested chain collaborating through
`this`. Here the blindness was *measurable* — the private-access gate reports
**zero** findings in that directory, not because the coupling is absent but
because a mixin merges into its host class and leaves no cross-module member
access to detect. A comparable decomposition elsewhere in the same addon is
measured, contract-declared and conformance-tested. This one was not measured at
all.

The same hole existed twice, in two languages, for the same structural reason,
and in both cases the surrounding gates reported clean.

## Decision

**Reconstruct the composition graph from the AST and ratchet it, in both trees.**

Each gate parses the compositions it governs, derives the collaboration graph the
import graph cannot show, and holds it against a pinned measurement — units,
edges, cycles, foreign accesses, shared private members — regenerated by the tool
rather than hand-maintained.

**Visibility before judgement.** Neither gate asserts the current graph is good.
It asserts the graph is *known*, so a mixin quietly acquiring a dependency on a
sibling is a diff rather than a discovery.

**The two trees are at opposite ends of the same technique, and only measurement
showed it.** The ORM's composition reports a largest strongly-connected component
of one — split until no mixin cycle remains. In the client, not one edge in
either measured composition is acyclic: the search model's units form a single
component in which every unit reaches every other. Same pattern, same fork, as
far apart as the metric goes.

**The worst knot and the volume of tangling are tracked separately.** Breaking
one back-edge of a cycle leaves the largest component unchanged while showing up
immediately in the edge count, which is what makes incremental progress visible
before a component splits.

**The gaming move is anticipated.** Every metric here falls to zero by folding
the mixins back into one class, which changes no coupling. The number of
participating units is reported alongside: a merge that "fixes" the graph shrinks
it in the same commit, where a reviewer sees both.

**Neither gate asks for the chain to be dismantled.** The client's mixin chain is
one of ADR-0021's four legitimate extension seams — downstream addons extend it
through `super`. The measurement exists to make growth deliberate, not to drive
the count to zero.

## Alternatives considered

**Extend the import-based gates to model inheritance.** Rejected: the
information is not there to extend. Multiple inheritance across mixins produces
no import edge by construction, so the checker would be replaced rather than
extended, and its contract model would have to change to serve a different
question.

**Rely on the private-access budget to surface it.** Refuted by measurement, and
the sharpest evidence here: that gate reports zero findings in the directory
holding the client's mixin chain. A mixin merges into its host, so member access
that would be cross-module anywhere else is formally access to `this`. The gate
is working correctly and cannot see this.

**Forbid mixin composition and use explicit delegation.** Rejected. It removes
the surface by removing the pattern, and the pattern is load-bearing in both
trees — the ORM's model assembly depends on it, the client's chain is a declared
extension point. Deleting a working seam to make a gate unnecessary inverts the
reason the gate exists.

**Ratchet nothing and document the graph in prose.** Rejected on standing
evidence: a property that is true and unenforced stays true until someone has a
reason (ADR-0016, ADR-0006). A prose graph also goes stale silently, which is
what a tool-regenerated `MEASURED` block prevents.

## Consequences

- The one coupling surface no edge-based gate can see is measured in both trees,
  and a new dependency between mixins appears in a diff.
- **A pinned graph must be regenerated, not edited.** Hand-editing reintroduces
  exactly the staleness the block exists to prevent.
- The measurement is descriptive. Neither gate says the graph should be smaller;
  a rising count is not automatically bad — the right reading is that the rise
  was intended and reviewed.
- Cycles among mixins are ratcheted rather than forbidden: the worst knot may not
  grow and shrinking it is locked in, but no gate demands zero. Requiring that is
  a much larger decision — the ORM reached a clean graph by splitting, and that
  work is a choice each composition makes on its own schedule.
- Coverage is the ORM's compositions and the client's; a mixin composition
  elsewhere is unmeasured, and nothing detects a new one appearing.
