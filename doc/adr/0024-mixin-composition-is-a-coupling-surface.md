# ADR-0024: Mixin composition is a coupling surface, and it has no import edges

- **Status:** Accepted
- **Date:** 2026-08-14 (retroactive — records decisions already enforced)

## Context

Every structural gate this fork has built reasons about **edges** — an import in
Python (ADR-0001, ADR-0005), an import or a registry lookup in the client
(ADR-0019), a module specifier or an inherited member (ADR-0020, ADR-0021). That
model is right for every boundary in `doc/architecture/module.md` except one.

**A mixin composition produces no edge at all.** In the ORM, `BaseModel` is
composed from a couple of dozen empty-`__slots__` mixins by multiple
inheritance; they collaborate through `self`, and a `self._fields` or a
`self._search` call inside one mixin resolves to a sibling mixin at runtime while
producing nothing an import checker can see. The most intricate coupling surface
in the framework was invisible to the checker guarding everything around it: a
mixin could grow a dependency on any other mixin and no gate moved.

The client has the same shape by a different mechanism. Its search model is
composed from five mixin factories in a nested chain, and they collaborate
through `this`. The blindness follows identically, and here it was *measurable*:
the private-access gate reports its findings across the whole addon and finds
**zero** in that directory — not because the coupling is absent, but because a
mixin merges into its host class and leaves no cross-module member access to
detect. A comparable decomposition elsewhere in the same addon is measured,
contract-declared and conformance-tested. This one was not measured at all.

So the same hole existed twice, in two languages, for the same structural reason,
and in both cases the surrounding gates reported clean.

## Decision

**Reconstruct the composition graph from the AST and ratchet it, in both trees.**

Each gate parses the mixin compositions it governs, derives the collaboration
graph that the import graph cannot show, and holds it against a pinned
measurement — units, edges, cycles, foreign accesses and shared private members —
regenerated by the tool rather than hand-maintained.

**The point is visibility before judgement.** Neither gate asserts that the
current graph is good. It asserts that the graph is *known*, so that a mixin
quietly acquiring a dependency on a sibling is a diff rather than a discovery.

**The two trees are at opposite ends of the same technique, and only measurement
showed it.** The ORM's composition reports a largest strongly-connected component
of one — it has been split until no mixin cycle remains. In the client, not one
edge in either measured composition is acyclic: the search model's units form a
single component in which every unit reaches every other. The same pattern, in
the same fork, as far apart as the metric goes. That contrast is the argument for
measuring rather than assuming, and neither side could have stated it before the
gates existed.

**The worst knot and the volume of tangling are tracked separately**, because
breaking one back-edge of a cycle leaves the largest component unchanged while
showing up immediately in the edge count — which is what makes incremental
progress visible before a component finally splits.

**The gaming move is anticipated.** Every metric here falls to zero by folding
the mixins back into one class, which changes no coupling at all. The number of
participating units is therefore reported alongside them: a merge that "fixes"
the graph shrinks it in the same commit, where a reviewer sees both.

**Neither gate asks for the chain to be dismantled.** The client's mixin chain is
one of the four legitimate extension seams recorded in ADR-0021 — downstream
addons extend it through `super` — and dismantling it to improve a number would
delete a working seam to satisfy a metric. The measurement exists to make growth
deliberate, not to drive the count to zero.

## Alternatives considered

**Extend the import-based gates to model inheritance.** Rejected because the
information is not there to extend: multiple inheritance across mixins produces
no import edge by construction, so the checker would not be extended but
replaced, and its own contract model would have to change to serve a different
question. Two gates with two models is the honest shape.

**Rely on the private-access budget to surface it.** Refuted by measurement, and
this is the sharpest evidence in the record: that gate reports zero findings in
the directory holding the client's mixin chain. A mixin merges into its host, so
member access that would be cross-module anywhere else is, formally, access to
`this`. The gate is working correctly and cannot see this.

**Forbid mixin composition and use explicit delegation.** Rejected. It would
remove the surface by removing the pattern, and the pattern is load-bearing in
both trees — the ORM's model assembly depends on it, and the client's chain is a
declared extension point. Deleting a working seam to make a gate unnecessary
inverts the reason the gate exists.

**Ratchet nothing and document the graph in prose.** Rejected on the fork's
standing evidence: a property that is true and unenforced stays true until
someone has a reason, which is the argument ADR-0016 made for the root modules
and ADR-0006 for countable gates generally. A prose graph also goes stale
silently, which is what a `MEASURED` block regenerated by the tool exists to
prevent.

## Consequences

- The one coupling surface that no edge-based gate can see is measured in both
  trees, and a new dependency between mixins appears in a diff.
- **A pinned graph must be regenerated, not edited.** Both gates carry a measured
  block produced by the tool; hand-editing it would reintroduce exactly the
  staleness the block exists to prevent.
- The measurement is descriptive. Neither gate says the graph should be smaller,
  and reading a rising count as automatically bad would be wrong — the right
  reading is that the rise was intended and reviewed.
- Cycles among mixins are ratcheted rather than forbidden: the worst knot may
  not grow, and shrinking it is locked in, but no gate demands it reach zero.
  Requiring that would be a much larger decision than measuring, and this record
  deliberately does not take it — the ORM reached a clean graph by splitting, and
  that work is a choice each composition makes on its own schedule.
- Coverage is the ORM's compositions and the client's; a mixin composition
  elsewhere in either tree is unmeasured, and nothing detects a new one
  appearing.

## Enforcement

Two gates in `tooling/architecture/`, each declaring `ADR = "0024"`, both run by
`.github/workflows/architecture.yml`:

| gate | measures |
|---|---|
| `tooling/architecture/mixin_coupling_check.py` | the ORM's mixin compositions, drift-zero against a pinned graph |
| `tooling/architecture/js_mixin_coupling.py` | the client's mixin chain, against its regenerated `MEASURED` block |

`tooling/architecture/test_gate_adr_coverage.py` checks that both citations
resolve to this record and that it is `Accepted`. For either graph's live
figures, run the gate — this record does not restate them.
